# AI 패효율 트레이너

## 한 줄 요약
Riichi-Trainer를 포크해, 그럴듯한 실전 국면에서 공개 마작 AI(Epsilon-Prism)의 판단으로 타패를 채점하고, 사용자가 선택한 CLI의 해설과 약점 기반 출제를 붙인 개인 학습용 트레이너를 만든다.

## 배경
- 기존 패효율 트레이너(Euophrys Riichi-Trainer)는 샨텐과 유효패 수만으로 정답을 정한다. 도라, 역, 점수 상황, 상대 리치·울기가 있을 때의 실전 최선과는 자주 갈린다.
- 상대는 손패 없는 고스트라서 수비와 밀기/접기 판단은 훈련할 수 없다.
- 2026-11 기준 강한 마작 AI 중 가중치가 공개되어 로컬에서 쓸 수 있는 것은 Epsilon-Prism v760(가중치 MIT)뿐이다. Mortal은 가중치를 공개하지 않는다. NAGA, LuckyJ, Suphx는 비공개다.

## 목표
- 순수 효율 최선과 AI 최선이 갈리는 국면을 문제로 낸다. 사용자 선택을 두 기준 모두로 채점한다.
- 상대 리치·울기가 포함된, 내부적으로 앞뒤가 맞는 국면을 합성한다.
- 틀린 문제에 대해 엔진 수치를 근거로 한 자연어 해설을 제공한다. 사용자는 Codex CLI, agy CLI(Antigravity), Claude Code CLI 중 해설에 사용할 도구를 선택할 수 있다.
- 오답을 유형별로 기록하고, 약한 유형을 더 자주 출제한다.

## 비목표
- 공개 배포. 본인 학습용이라 배포·라이선스 표기와 다국어 정비는 하지 않는다.
- 온라인 대국 보조. Epsilon 저자의 요청(실전 대국에 쓰지 말 것)을 지키고, 대국 클라이언트 연동은 만들지 않는다.
- 자체 AI 학습. 기존 모델의 추론만 쓴다.
- 3인 마작. 4인 반장 기준으로만 만든다.

## 제약
- 기반 코드: Riichi-Trainer(React/CRA, JavaScript, GPL-3.0)를 포크한다. 샨텐·유효패 계산은 `src/scripts/ShantenCalculator.js`, `UkeireCalculator.js`에 있다.
- AI 판정기: Epsilon-Prism v760. Java 21 + DJL(PyTorch 백엔드)로 돌아가고 Python API가 없다. 첫 실행 때 libtorch(압축 해제 시 약 1.5GB)를 받는다. CPU만으로 동작하고 메모리는 약 2.5GB를 쓴다.
- Epsilon의 출력: 후보 타패별 순위 가치 추정값이다. 보상은 1~4위 = 2/3, 1/3, 0, −1이다(2026-11-26 정정: 처음에 "2, 1/3, 0, −1"로 잘못 적었다. 모델 zip의 README 기준). 전체 후보 값은 T1에서 받을 수 있음을 확인했다.
- 추론 실행: 로컬 Python 서버.
- 해설 LLM: 서버가 사용자 선택에 따라 Codex CLI, agy CLI 또는 Claude Code CLI를 비대화형 하위 프로세스로 실행한다. 각 CLI의 기존 로그인 설정으로 인증한다.
- 해설 경로에는 CLI 실행 시간, 스트림 연결 시간, 출력 대기 시간에 대한 앱 타임아웃을 설정하지 않는다. CLI가 정상 종료하거나 오류를 반환하면 스트림을 닫는다. 사용자가 해설을 취소하면 스트림과 해당 CLI 프로세스를 종료한다.
- 플랫폼: Windows 11.

## 성공 기준
- 문제 하나를 열면 1초 안에 표시된다. 문제은행에서 미리 생성해 둔 국면을 쓰기 때문이다.
- 타패 직후 효율 기준(유효패 수)과 AI 기준(최선 대비 가치 손실)이 함께 표시된다.
- 채점 결과의 해설 버튼 옆에서 CLI를 선택할 수 있고, 서버는 선택한 CLI로 요청을 실행한다. 실행할 수 없는 경우 해당 CLI와 오류를 표시해 사용자가 다른 CLI를 고를 수 있게 한다.
- 세 CLI 각각의 해설 완료 시간 목표는 요청 후 15초 이내다. 15초가 지나도 생성 중인 해설은 계속 받을 수 있어야 한다.
- CLI가 해설을 생성하는 동안 서버에서 브라우저로 스트리밍한다. 모든 CLI에 같은 수치 검증을 적용하고, 수치의 문맥을 확인할 수 있는 단위로 검증이 끝난 내용부터 표시한다. 화면에서 생성 중, 완료, 오류, 취소 상태를 확인할 수 있다.
- 구현 검증에서 각 CLI의 부분 출력이 종료 전에 화면에 도착하는지 확인한다. 출력이 15초 넘게 지연되는 경우와 사용자가 중간에 취소하는 경우도 검증한다.
- 문제은행에서 효율 최선과 AI 최선이 다른 국면의 비율을 필터로 조절할 수 있다.
- 오답 유형 통계가 세션을 넘어 유지된다.

## 선택한 접근과 근거
- 접근 A로 시작한다. 사용자가 고른 B안(랜덤 생성 + 그럴듯한 상태 합성)의 정신은 지킨다. 다만 무작위 합성 대신 AI 자기대국에서 국면을 뽑는다. 리치·울기까지 넣으면 합성 상태의 정합성이 AI 채점의 신뢰도를 좌우하기 때문이다.
- Epsilon과는 리뷰어 백엔드(v760 태그 소스를 javac로 컴파일)를 상주하는 stdio 자식 프로세스로 띄워 연동한다. 호출마다 JVM과 libtorch를 새로 띄우면 수 초씩 걸리기 때문이다. 처음에는 Java 브리지를 직접 만들 계획이었지만, T1에서 리뷰어에 같은 역할의 stdio 호스트가 이미 있는 것을 확인해 그쪽으로 바꿨다.
- 게임 진행과 국면 직렬화에는 Epsilon 자체 시뮬레이터를 우선 검토한다. 맞지 않으면 RiichiEnv(Apache-2.0, Python)를 쓴다.
- 프런트엔드는 포크한 Riichi-Trainer의 손패 렌더링과 패 이미지를 재사용한다. 문제 로딩과 채점은 Python 서버 API로 바꾼다. 효율 계산은 기존 JS 코드를 그대로 쓴다.
  - 2026-11-26 정정(T4 착수 시): 포크하지 않고 Vite + React로 새로 만들었다. Riichi-Trainer는 React 16과 react-scripts 3.4(webpack 4)라서 Node 22에서 legacy OpenSSL 옵션이 필요하고 오래된 의존성이 많다. 가져온 것은 패 이미지(CC BY 4.0)뿐이다. 효율 계산은 이미 Python으로 문제은행에 들어 있어 JS 코드를 재사용할 이유가 없어졌다.
- 오답 기록은 서버의 SQLite에 저장한다.

## GPU 가속 조사 (2026-11-26)
- v760 릴리스 jar는 NVIDIA GPU에서 돌지 않는다. Prism 추론이 매 층 부르는 `packedRelationScaledDotProductAttention`은 djl-rocm JNI 안에 있는데, GPU 구현이 ROCm(AMD) 빌드에만 있다. CUDA JNI를 받아 넣어 봐도 같은 오류가 났다.
- Epsilon main(11-25)에는 NVIDIA용 자체 CUDA 추론 커널(`epsilon-prism-kernel/cuda`, `inference.kernels = "NATIVE"`)이 있다.
  - `scripts/build-epsilon-cuda.ps1`로 sm_89용으로 빌드했다. djl-rocm은 GitHub Packages에 있어 `read:packages` 토큰이 필요하고, CMake는 Ninja 생성기를 써야 한다.
  - v760 가중치는 main에서 그대로 열린다. main 테스트가 v760의 스키마 지문을 단정한다.
- 실측(자기대국 `records`):
  - CPU v760: 16반장 183초, 판단 50/s.
  - GPU main: 16반장 18.4초(605/s), 256반장 18.0초(9,226/s, 배치 143행, GPU 메모리 2.6GB).
  - GPU로 만든 천봉 XML 16개는 v760 리뷰어의 재생 검증을 모두 통과했다.
- 판단: 자기대국 생성은 main + CUDA로 옮긴다. 이제 병목은 v760 리뷰어의 CPU 분석(엔진 4개 175/s)이다.

- 리뷰어 GPU(2026-11-26): `EngineConfig.gpu_main()`으로 main 리뷰어를 GPU BF16 NATIVE로 돌린다.
  - 프로토콜은 그대로 통한다. 결과 형식 7은 3인용 nuki(행동 372)만 늘었다.
  - 차이 1: main의 mjai 리더는 `hora.deltas`를 요구한다. 그래서 `tools/selfplay`가 쓴 기존 mjai 118반장은 v760 리뷰어로만 분석할 수 있다. main `records`의 천봉 XML은 두 리뷰어 모두 읽는다.
  - 차이 2: 한 버림패에 여러 좌석이 응답할 때 판단의 순서가 v760과 다르다.
  - 속도: 반장 하나는 GPU 13.5초, CPU 14.5초로 거의 같다. 리뷰어가 한 반장의 판단을 차례로 돌려 배치가 작기 때문이다. 엔진 8개 병렬이면 GPU 322/s, CPU 213/s(약 1.5배)다.
  - 정밀도: 927판단 중 BF16과 FP32의 손실 차이가 0.01 이상인 것은 1개였고, 최선수가 바뀐 판단은 동률 근처뿐이었다.

- 배치 분석 도구(2026-11-26, `tools/batch-review`):
  - 리뷰어의 `Analysis`와 `ResultWriter`를 재사용하고, 반장마다 스레드를 둔다. 평가 요청은 `NetworkPolicy.submit`으로 한 배치에 모은다.
  - 256반장을 스레드 256개로 21.6초에 분석했다(7,681판단/s, 배치 141행). 리뷰어 GPU 엔진 8개 대비 약 24배다.
  - 출력이 리뷰어 결과 문서와 같아서 Python 쪽은 고치지 않았다. 리뷰어 출력과 2,295판단을 대조해 차이가 0이었다.
  - 버린 대안: 시간 제한으로 배치를 내보내는 방식. 모든 작업 스레드가 기다리는 순간이 곧 더 모일 요청이 없는 순간이므로, 시간 제한은 지연만 늘린다.
- 문제은행: GPU 256반장(`gpu-` 접두사)을 더해 374반장, 184,293문제가 됐다. GPU분과 CPU분의 불일치 비율이 36.7%와 36.9%로 같다.

## 미결정
- 이제 병목은 Python의 문제 추출(효율 계산)이다. 256반장에 303초가 걸려 GPU 분석(21초)의 약 14배다. 문제를 더 늘릴 때 multiprocessing으로 나누면 된다.
- (해결, 2026-11-26 T1) 전체 후보 값은 리뷰어 결과 문서에서 받을 수 있다. 입력은 천봉 XML, mjai, 작혼의 완전한 패보다. 연동은 상주 Java 브리지를 새로 만들지 않고 리뷰어의 stdio 호스트를 재사용하는 쪽으로 바꿨다.
- 리뷰어의 `scenario`(가정 국면 재분석)로 상대 리치·울기 국면을 직접 합성할 수 있는지. 되면 자기대국 패보에 기대는 정도를 줄일 수 있다.
- (해결, T5) 첫 분류는 문제은행에 기록된 상대 리치 대응, 울기 손, 문전 손이다. AI 손실 0.01 이상을 복습 대상으로 세며, 도라·역·안전도에 관한 원인 분류는 보류했다.
- 실시간 대국(B)의 후속 요구사항은 [동일 패산 멀티플레이 동풍전 브리프](2026-11-26-multiplayer-east-series.md)에 정리했다.
