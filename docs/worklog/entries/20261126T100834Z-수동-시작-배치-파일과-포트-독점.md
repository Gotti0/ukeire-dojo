## 배경

사용자는 재부팅 뒤 자동 시작(작업 스케줄러)을 원하지 않고, 서버를 수동으로 켜기로 했다. 더블클릭으로 켤 수 있는 배치 파일이 필요했다.

## 문제

- 배치 파일로 시험 서버(5180)를 띄우자 시작부터 실패했다. serve-public.ps1이 Tee-Object로 `data/server-access.log`를 독점으로 열었는데, 이미 돌고 있는 5173 서버가 같은 파일에 덧붙이고 있었다.
- 그 뒤에는 5180이 응답하지 않았다. 원인은 같은 포트에 Python 프로세스 두 개가 함께 바인드해 연결을 나눠 가진 것이었다. HTTPServer는 SO_REUSEADDR를 켜는데, Windows에서는 이 옵션이 다른 프로세스의 중복 바인드를 허용한다. 배치 파일을 두 번 실행하면 서버 두 개가 조용히 같은 포트를 나눠 쓴다.
- Windows PowerShell 5.1(pwsh가 없을 때 쓰는 쪽)은 Stop일 때 `2>&1`로 받은 stderr를 종료 오류로 바꾼다. 서버의 접속 기록이 stderr라서 첫 줄에서 서버가 끊길 수 있었다.

## 결정과 근거

- `serve-public.bat`은 ASCII와 CRLF로만 쓴다. cmd가 배치 파일을 OEM 코드 페이지로 읽어서다. pwsh가 있으면 pwsh를, 없으면 powershell을 부르고, ExecutionPolicy Bypass는 그 프로세스에만 준다. 오류로 끝나면 pause해서 창이 바로 닫히지 않게 했다.
- Tee-Object는 버렸다. 서버에 `--log-file`을 두어, stderr와 함께 줄마다 덧붙이기 모드로 파일에 직접 쓴다. stderr를 파이프로 받지 않으니 PS 5.1의 stderr 문제도 사라진다.
- 서버 클래스는 Windows에서 SO_REUSEADDR를 끄고 SO_EXCLUSIVEADDRUSE를 건다. 두 번째 실행은 "이미 사용 중"으로 바로 실패한다.
- 시험 환경에서 배운 점: 이 도구 환경은 `NoDefaultCurrentDirectoryInExePath=1`이라 cmd가 현재 폴더의 배치 파일을 이름만으로 실행하지 않는다. 또 백그라운드 도구에는 실제 콘솔이 없다. 그래서 최종 확인은 `Start-Process`로 별도 콘솔을 열어 더블클릭과 같은 조건에서 했다.

## 검증

- 기존 클래스(ThreadingHTTPServer)로는 같은 포트의 두 번째 바인드가 성공하는 것을 확인했다. 새 Server 클래스는 OSError로 실패한다(테스트 추가, 서버 테스트 16개 통과).
- 별도 콘솔에서 `serve-public.bat -Port 5180`을 실행했다.
  - API는 200, 암호 없음은 401, 패 이미지 38장 병렬 요청은 모두 200이었다.
  - 시작 줄과 요청이 공유 로그에 기록됐다. 그동안 5173 서버도 계속 응답했다.
- 5173이 사용 중일 때 새 서버를 띄우면 "cannot listen … Is another server already running?"을 내고 종료 코드 1로 끝났다. 5173의 수신 프로세스는 1개로 유지됐다.

## 미해결

- 지금 5173에서 돌고 있는 서버는 고치기 전의 클래스로 띄운 것이다. 다음에 배치 파일로 켤 때부터 포트 독점이 적용된다.
- 더블클릭으로 연 창을 사용자 화면에서 직접 확인하지는 않았다. 숨긴 별도 콘솔로 같은 조건을 재현했다.
