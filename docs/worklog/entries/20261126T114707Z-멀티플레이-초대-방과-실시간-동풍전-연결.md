## 배경

T8은 한 방의 두 동풍전 상태와 국·본장별 공통 패산 재사용을 구현했다. T9에서는 이를 브라우저와 Python 서버에 연결해 사람 2~4명이 초대 방에서 실시간으로 동풍전을 진행하고 새로고침 뒤 복귀할 수 있어야 했다.

## 문제

Python 서버가 Java 규칙 엔진과 Prism GPU 추론을 직접 호출해야 하며, 1단계 트레이너만 쓰는 실행에서는 GPU 모델을 미리 올리지 않아야 한다. 또한 각 좌석의 응답에는 타인의 손패, 패산, 시드, 타인 토큰이 절대 노출되면 안 되고, 연결 끊김 감지 지연이 길면 이탈 유예 타이머가 늦어진다.

## 결정과 근거

- 단일 스레드 상주 Java 호스트를 두고 첫 멀티플레이 방 시작 시에만 지연 기동하도록 했다. 표준 출력을 프로토콜 전용으로 분리해 라이브러리 로그 오염을 막고, 좌석 상태는 `SeatView`와 본인 결정만 직렬화해 비공개 정보를 원천 차단했다.
- 참가자 인증은 URL 쿼리 대신 요청 헤더 토큰과 탭 단위 `sessionStorage`로 분리해 접속 로그 노출을 막고 한 PC의 두 브라우저 탭에서도 서로 다른 좌석으로 테스트할 수 있게 했다.
- 실시간 상태는 기존 HTTP 서버의 NDJSON 스트림으로 전달하고, 소켓 가독성 확인(`MSG_PEEK`)으로 0.25초 안에 연결 끊김을 감지한다. 유예 시간(기본 15초)을 넘기면 AI가 임시 대타를 맡아 진행하고, 같은 토큰으로 재접속하면 다음 선택부터 즉시 복귀한다.

## 검증

- Java 통합 검증 4개(`EastMatchTest` 및 좌석 분리·스크립트 대국)가 통과했다.
- Python 테스트 60개(기존 55개 + 방 입·퇴장·방장 승계·좌석 정보 분리·중복/지연/불법 입력 거부·유예 초과 AI 대타 및 재접속·동풍전 완주·실제 Prism GPU 추론)가 통과했다.
- Vite 프로덕션 빌드와 실제 Prism GPU(`gpu0`)를 띄운 2브라우저 Chromium E2E에서 방 생성·입장·시작·타패 실시간 반영·새로고침 복귀·1단계 트레이너 회귀를 확인했다.

## 미해결

- 두 번째 경기 시작, 요청형 타패 추천, 두 경기 결과 비교는 T10 범위로 남아 있다.
