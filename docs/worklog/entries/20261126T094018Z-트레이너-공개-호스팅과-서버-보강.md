## 배경

T4 서버는 localhost 전용으로 설계했다. 사용자가 5173 포트를 DDNS로 공개하고, 접근은 본인과 지인으로 한정하기로 했다(공유 암호).

## 문제

- 5173은 Vite 개발 서버의 포트다. 개발 서버는 공개용이 아니다.
- T4 서버는 공개용 보호 장치가 없었다. 인증, 속도 제한, 본문 크기 제한, 소켓 시간 제한, 접속 기록이 모두 없었다.
- T4에서 "ORDER BY random()은 18만 행에서도 수십 ms"라고 판단했는데, 틀렸다. 인덱스를 못 타는 필터 조합에서 요청당 약 0.5초(537ms)가 걸렸다. 공개 서버에서는 요청 몇 개로 서버를 붙잡을 수 있다.

## 결정과 근거

- Vite 개발 서버를 공개하는 안은 버렸다. 빌드한 화면과 API를 Python 서버 하나가 0.0.0.0:5173에서 서빙한다.
- HTTPS 리버스 프록시(Caddy)는 사용자가 고르지 않았다. HTTP라 Basic 인증 암호가 평문으로 오가는 위험은 사용자에게 알렸다. 대응은 전용 무작위 암호(24자)로 한정하는 것이다.
- 인증: 공유 암호 하나를 쓰고 사용자 이름은 보지 않는다. 비교는 상수 시간이다. 외부 주소로 열면서 암호가 없으면 서버가 시작하지 않고, 12자 미만 암호도 거부한다.
- 출제: ORDER BY random()을 버렸다. 시작할 때 (disagree, opp_riichi, menzen) 8칸을 eff_loss로 정렬해 메모리에 올리고(약 0.6초), 요청마다 이진 탐색으로 고른다. 칸이 달라도 문제마다 같은 확률이다.
- 그 밖에 IP별 토큰 버킷(초당 5회, 순간 30회), 본문 4KB 제한, 소켓 15초 시간 제한, nosniff와 no-store 헤더, 접속 기록을 넣었다.

## 검증

- 서버 테스트가 6개에서 13개로 늘었고 모두 통과했다. 추가한 것은 다음과 같다.
  - 출제 필터와 균등성(12,000회 ±15%)
  - 토큰 버킷 충전
  - 401(암호 없음, 틀림, 잘못된 base64)과 200(맞음)
  - 429, 413, 보안 헤더
  - 암호 없이 외부 주소로 열거나 짧은 암호로 열 때 시작 거부
- 실제 문제은행으로 0.0.0.0:5173에 띄워 확인했다.
  - 암호 없음과 틀림은 401, 맞음은 200이었다.
  - LAN 주소로 문제 API를 부르면 3ms에 200이 왔다. 같은 최악 필터가 이전에는 537ms였다.
  - 접속 기록이 남는 것을 확인했다.

## 미해결

- 외부(인터넷)에서 들어오는 접속은 확인하지 못했다. Windows 방화벽 인바운드 허용과 공유기 포트 포워딩이 필요하고, 사용자가 직접 설정한다.
- HTTPS가 없다. 공용 와이파이 등에서는 암호가 노출될 수 있다.
- 서버는 세션이 띄운 백그라운드 프로세스다. 재부팅 뒤 자동으로 시작하는 설정(작업 스케줄러 등)은 하지 않았다.
